# Security Policy

## Supported Versions

| Version         | Supported          |
| --------------- | ------------------ |
| Latest release  | :white_check_mark: |
| Older releases  | :x:                |

Fixes ship in a new release rather than as patches to earlier versions.

## Reporting a Vulnerability

1. **Do NOT** create a public GitHub issue.
2. Open a private report:
   <https://github.com/kkdev92/plantuml-local/security/advisories/new>

   That is the **"Report a vulnerability"** button in this repository's Security
   tab; the link goes straight to it. Private reporting is enabled, so the
   advisory stays between us until there is a fix to describe.

Reports are looked at on a best-effort basis; please allow a reasonable disclosure window.

## Security Model

This extension is designed so that **diagram source is rendered locally and is not sent to an external service**. The measures below implement that design.

### Non-goals

State the limits up front, so the guarantees below are read for what they are:

- The render worker is an isolation boundary for JavaScript globals, **not a process- or OS-level security sandbox**. Code running in it has the same OS privileges as the extension host.
- Stubbing browser-style network APIs is not the same as closing every network path available to Node.js. It removes the paths the rendering engine actually uses; it is a hardening measure, not a kernel-level egress block.
- The extension is not a defence against a malicious VS Code extension, a compromised extension host, or a hostile machine.

### No network I/O

- The rendering engine (`@plantuml/core`), the Graphviz WebAssembly and all runtime assets ship inside the VSIX and are loaded from disk.
- **Network APIs are disabled inside the render worker**: `fetch`, `XMLHttpRequest`, `WebSocket` and `EventSource` are replaced with throwing stubs before the engine loads (`src/worker/network-guard.ts`). The engine files contain two places that could load something: in `plantuml.js`, the `<script>` element it adds for a library it has not been given, which the worker answers before the element is made (see *The standard library is served from the package* below); and in `viz-global.cjs`, the `fetch` Emscripten emits for loading a WebAssembly binary that is in practice embedded in the file. With these measures in place, reaching either fails the render instead of making a request.
- Neither bundle contains a rendering-service URL; `scripts/verify-vsix.mjs` checks every package for `plantuml.com/plantuml` / `kroki.io` references and CI runs it on each build.
- There is no telemetry of any kind.

### Rendering is isolated in a worker thread

The engine requires `window` / `document` globals. They are created inside a `worker_threads` worker, never on the extension host's `globalThis`, so no other extension's environment detection is affected, and a crashing render cannot take the extension host down. As noted under non-goals, this isolates globals and contains hung renders — it is not a security sandbox.

### The preview receives only sanitised, static SVG

The Markdown preview webview runs none of this extension's code — no `previewScripts` are contributed. Before an SVG leaves the worker it is parsed as `image/svg+xml` and stripped of:

- script-bearing elements (`<script>`, `<foreignObject>`, `<iframe>`, `<embed>`, `<object>`)
- event handler attributes (`on*`) — on every element including the root `<svg>`
- `href` / `xlink:href` / `src` values that are not in-document fragment references (`#…`) — this covers `javascript:` and `data:` URIs, and the `<a href>` / `<image href>` output of PlantUML's `[[url]]` hyperlink and `<img:url>` creole syntax
- processing instructions and comments. The engine appends a `plantuml-src` processing instruction to every SVG, holding the diagram source compressed but not encrypted: comments, preprocessor variables and the names of elements hidden with `hide` all decode back out of it. PlantUML's command line leaves it out with `-nometadata`; the browser engine this extension bundles has no such option
- `data-*` attributes, in which the engine records element names — aliases and elements hidden with `hide` among them — and the source line each element came from. Nothing draws them
- the `<a>` element of a `[[url]]` link that leads out of the diagram, whose `title` repeats the target, which `[[url label]]` does not draw. What the link draws stays
- markup that loads or navigates with no link attribute: `<style>`, `<meta>` (a refresh), `<link>` and `<base>`, and the value of `style` or of a presentation attribute that takes a URL (`fill`, `stroke`, `filter`, `clip-path`, `mask`, `marker-*`, `cursor`) when it calls any CSS function but `url(#…)`. Every way CSS has of loading something is a function, and a function needs a `(` as written, so this holds however the value is escaped. The engine writes none of these: it is here for an engine that one day passes markup through

Element and attribute names are judged by the part after their prefix, whatever the prefix and whatever it is bound to, because that is how a browser opening an exported file reads them: with `s` bound to the SVG namespace, `<s:script>` is a script, and with `x` bound to xlink, `x:href` is a link.

The export commands write this same sanitised SVG, which matters most there: an exported file is shared with people who never see the Markdown. What the diagram itself draws — labels, names, notes — is of course still in the file; this removes what the engine adds on top of the drawing, and is not a way to anonymise a diagram.

Error messages and user source shown in error boxes are HTML-escaped.

#### The one exception: rasterised sprites

PlantUML draws `sprite` definitions — the mechanism behind icon sets such as Azure-PlantUML — by rasterising them and emitting the result as an inline PNG on an `<image>`. Stripping that link leaves an image element with no image, so the icon renders as blank space. The sanitiser therefore keeps a link value that meets **all** of the following:

- the element is `<image>`, and the attribute is `href` or `xlink:href` — never `<a href>`, so no navigation path is opened, and never `src`
- the value matches `data:image/png;base64,` followed only by base64 characters, so it cannot carry a second URI or break out of the attribute
- the payload begins with the PNG signature, so a `data:` URI merely *labelled* `image/png` does not qualify

`data:text/html`, `data:image/svg+xml`, `javascript:` and remote URLs remain blocked. The reasoning for allowing this much: a PNG cannot carry script the way an SVG can; the bytes are inline rather than fetched, so the network-egress concern behind the general rule does not apply; and the Markdown preview's default Content-Security-Policy already permits `img-src … data:` while confining scripts to a nonce.

#### The `.puml` preview panel

The preview of a `.puml` file is a webview of this extension's own, and runs two scripts, `media/viewer/viewer.js` and the zoom it takes from `media/viewer/zoom.js`. It receives the same sanitised SVG and shows it through an `<img>` holding a Blob URL, so the SVG is treated as an image: nothing in it can run, even something the sanitiser missed. The PNG its Copy button puts on the clipboard is drawn the same way: the page reads the SVG as an image from a Blob URL, draws it onto a canvas and writes the PNG to the clipboard. The panel's Content-Security-Policy is `default-src 'none'` with scripts allowed by nonce only and images from the panel's own source, `data:` and `blob:`; it may load files from `media/viewer` only, and has forms disabled. The page acts only on messages carrying its own origin, which is how VS Code's frame around it delivers the extension's messages. The messages it sends back are untrusted input: only a ready notice, a choice among the file's diagrams, and the requests of its PNG, Copy and Copy SVG buttons are acted on; a request names no file and no path, and acts on the diagram the panel shows, as found in the file's current text. So is the state it keeps for a restart — the file's URI and the diagram's name, which the extension reads, and each diagram's zoom, which only the page does: a panel whose state does not hold a URI that opens is closed rather than restored, and a restored panel's options are set again rather than taken from the saved session.

#### The PNG panel

*Export Diagram as PNG* draws the PNG in a webview of this extension's own, since the extension host has no canvas. The page runs one script, `media/png/png.js`. It receives the same sanitised SVG and reads it as an image from a Blob URL, so nothing in it can run; it draws that image onto a canvas and sends the PNG back as bytes. The panel's Content-Security-Policy is `default-src 'none'` with scripts allowed by nonce only and images from the panel's own source, `data:` and `blob:`; it may load files from `media/png` only, and has forms disabled. It keeps its page while hidden behind another tab, so the PNG still comes back, and it is closed once it does, or after 30 seconds without it. *Export All Diagrams in Folder as PNG* draws its PNGs one after another in one such panel, which it closes after the last, or after 30 seconds without one. The page acts only on messages carrying its own origin. What it sends back is untrusted input: only a ready notice, the PNG's bytes and an error are acted on, and the bytes are written only when they begin with the PNG signature and a header of the size that was asked for, and come to no more than 64 MiB.

### Hovers, completion details and parameter hints show the text of documents as written

A hover in a diagram can show text from the document and the files it includes: the declaration of a procedure, a function or a variable, the comment lines above it, and the path of an include. The details of a suggested procedure, function or variable show the same: its declaration, where it is and the comment above it; the parameter hints of a call show where each definition of the name is and its comment. Each of them is a `MarkdownString` with `isTrusted` and `supportHtml` false (`src/extension.ts`), so VS Code runs no `command:` link in it and strips raw HTML. The text of the documents goes in escaped — each ASCII punctuation character behind a backslash — or as code, in a fenced code block or a code span marked by a run of backticks longer than any in it (`src/language/hover.ts`), so that nothing in it is read as a link, an image or HTML: a link or a remote image in a comment is shown as the text it is, and not followed or loaded. The built-in help of directives, kinds of diagram, themes, icons, the snippets of the completion, and style properties and skinparams ships with the extension, and nothing is fetched to show it; the names of the style properties are read from the bundled engine when the extension is built. To say which file an include reads, a hover asks for it as a render does, under the checks of *Included files are chosen by the extension* below.

### Remote references are rejected up front

`!include https://…` and `!theme … from https://…` never reach the engine; the block renders an explanatory message instead.

### Included files are chosen by the extension

The engine reads no file itself. For each local `!include`, `!include_once`, `!include_many` and `!includesub` it runs, and each `!theme … from` a folder, it asks the host through `PLANTUML_FILE_LOADER`, and the worker passes the request to the extension host, which decides (`src/includes/`). A file is delivered only when all of these hold:

- the workspace is trusted, and the document is a saved file on disk in a workspace folder;
- the path, as the engine hands it over, is relative: an absolute path, a drive, a share, a URI or `~` is refused, as are a device name, a name ending in a dot or a space, a `:` in a name, a control character and a `.git`, `.hg` or `.svn` folder, and nothing in the path is decoded or expanded;
- the path is looked for next to the including file, then in the folders of `plantumlLocal.includePaths`, and every place looked at lies inside the document's workspace folder, taken by its real path; one that leaves it stops the include rather than letting a file elsewhere stand in;
- no name between the workspace folder and the file is a symbolic link or a junction, checked with `lstat` name by name, and the file's real path lies inside the workspace folder too;
- it is a regular file ending in `.puml`, `.plantuml`, `.pu`, `.iuml`, `.wsd`, `.inc` or `.txt`, holding valid UTF-8 without a NUL;
- one diagram's includes stay within 32 levels, 2048 files and 16 MiB in all.

`plantumlLocal.includePaths` is declared a restricted setting, so a workspace's own value is not used in Restricted Mode. A document open in the editor is delivered with its unsaved changes. Within one export — the diagrams of a document, or of every document of a folder — each file is read once, under these checks, and that first read answers every later request for it: its text, that it was missing, or why it was refused; so do the trust, the folder and the setting a document's includes were first looked for with. Each diagram is still held to the limits above by itself. Just before it writes an image, the export asks for the same files again as they are then — the trust, the folder and the setting looked up again, each request under the same checks and limits, an open document with its unsaved changes — and compares what it finds with what the image was drawn from; it keeps none of it. The checks bound which files are read; they do not judge what is in them, and anything in a readable file of the workspace folder can end up in a diagram.

The *Diagram Dependencies* view lists what drawings asked for — the paths, the files read and the places looked at — as the drawings recorded it; for a diagram with no drawing, it draws one as the Problems panel does, under the checks above. Its commands act only on items the view made (`src/includes/dependency-view.ts`). Before it opens a file a drawing read, or the file that asked for another, it finds that file again as a drawing reaches one — in a trusted workspace, a regular file inside the document's workspace folder, through no symbolic link or junction — so it opens none in Restricted Mode; it goes to a line of a document only while the document is as it was when the item was listed.

### Go to Symbol in Workspace reads files only when a query is typed

Go to Symbol in Workspace (`Ctrl+T`) lists the diagrams and declarations of the Markdown and PlantUML files of the workspace folders (`src/language/workspace-symbol-provider.ts`). Nothing is read until a query is typed, and nothing at all in Restricted Mode or from a folder that is not on disk. The first query walks the workspace folders as exporting a folder does — skipping `.git`, `.hg`, `.svn`, `node_modules`, `dist`, `build` and what `plantumlLocal.workspaceSymbols.exclude` names, and following no symbolic link or junction — and reads each Markdown, `.puml`, `.plantuml`, `.pu`, `.iuml` and `.wsd` file with the checks of an include: no symbolic link or junction on the way, its real path inside the workspace folder, a regular file of valid UTF-8 without a NUL, and here no more than 2 MiB and 50,000 lines. It draws nothing and follows no `!include`. One walk reads at most 500 files, lists at most 10,000 folders and 100,000 entries, goes at most 64 folders deep and stops after 30 seconds, and says so when it stops short. Only what it found in each file is kept, in memory, with a SHA-256 of the file's text but not the text. Later queries are answered from it, with the unsaved text of open documents; a file changed on disk is read again at the next query, a file created or deleted makes it walk again, and picking a name reads its file again, the same way, to find the name. `plantumlLocal.workspaceSymbols.enabled` and `plantumlLocal.workspaceSymbols.exclude` are declared restricted settings, as `plantumlLocal.includePaths` is.

### The standard library is served from the package

`!include <azure/…>` and `!include <C4/…>` resolve against copies of those libraries baked into the VSIX. Left to itself the engine reacts to an unknown library by appending `<script src="azure.min.js">` to its document and waiting, which would mean either a network request or a render that hangs until the timeout. The worker pre-populates the globals the engine reads (`window.PLANTUML_STDLIB` and friends) so that path never runs, and makes any `<script>` the engine still creates report failure immediately — so `!include <aws/…>`, which is not bundled, produces a prompt error instead of a stalled render. The `!theme` library and the OpenIconic icons are served the same way: the worker loads the copies in the VSIX and marks them loaded, so the engine never asks for `themes.js` or `openiconic.js`. Emoji are not bundled, and a diagram using one fails at once with a message.

### Untrusted and virtual workspaces

The extension declares limited support for untrusted and virtual workspaces: it spawns no processes and executes nothing from the workspace. In an untrusted workspace it reads no workspace files, and a local `!include` fails with a message saying so; in a virtual workspace it reads none either, as only files on disk are included or searched. The only input it processes then is the text of ` ```plantuml ` fences and PlantUML files, inside a worker, with the output sanitised as above.

Exporting is the one path that writes files: the export commands write SVG and PNG files, and *Export All Diagrams as SVG and Update Image Links* also edits the Markdown buffer. Naming a diagram from the light bulb and *Insert Diagram Template* edit the document only when asked, as typing would, and work in any workspace; so does renaming a participant's alias with Rename Symbol, in a Markdown file on disk or an untitled one, which reads and changes that document alone. Exporting a folder also reads the Markdown and PlantUML files under it, following no symbolic link or junction. All of them refuse to run in an untrusted workspace, enforced by a runtime `workspace.isTrusted` check rather than by hiding the commands — a hidden command can still be invoked programmatically. Rendering and the preview are unaffected. The destination comes from `plantumlLocal.exportDirectory`, which must be a relative path without `..`, and file names come from the block's own name, restricted to letters, digits, hyphens and underscores; neither can be made to point outside the document's folder. To replace their own files without asking while still asking about any other, the export commands keep a record in the workspace's state on this machine (`src/export/history.ts`): for each file they wrote, its URI, the diagram it was written for — the document's URI, where the diagram's name comes from, the name and the format — and a SHA-256 of the bytes written. With it goes, when the drawing could tell, what the image was drawn from (`src/export/manifest.ts`): a SHA-256 of the diagram's text and of what the engine was given; the workspace folder, the document's folder and the search folders, or why no file could be read; each file the diagram asked for — the path as written, the file that asked, the answer and the paths looked at — and each file delivered, by its path, a SHA-256 of its text and whether that text came from the disk or an editor; the files of the bundled libraries read; the engine's version and a SHA-256 of the files that draw; the format, the palette and the PNG scale; whether the image leaves out some of the diagram; and whether the same text and files are known to draw the same image again, with the line and the name of each directive or `%` function that may not. No diagram source, no file's text and no image is recorded. A file is replaced without asking only when the record names the same diagram and the file's bytes still match. Each record, what the image was drawn from included, is checked field by field as it is read, and one that is not as the extension writes it, or one of two for the same file, grants nothing; the records are kept by file in a `Map`, so no name in them is taken as a property of an object. Records written by a later version are read as none and left as they are. At most 2,000 files and 16 MiB are recorded; past that, and when the state does not take a record, the file is written but not recorded, and the next export asks about it. The record that earlier versions kept — the document's URI and the SHA-256, per file — is read and no longer written: a file only it knows is replaced once that is confirmed. A file open with unsaved changes is not written. Within one window, a file is written by one export at a time, each looking at the file and its record again before writing; other windows and programs are not held off, and a change they make is caught by that second look unless it falls between the look and the rename that puts the new file in place. A file on disk is replaced by the file system's own rename, in one step; where that cannot be done — another program has the file open, say — VS Code's rename, which deletes the old file first, is used, as before, unless a folder has taken the file's place by then, which it would delete with all it holds. The images an export has drawn are held in memory until they are written, up to 64 MiB in all, and past that in temporary files, each in the folder its image goes to — a folder under the document's that the export writes to anyway, made if it is not there, as writing the image would make it. An image is written from such a file only when the file's size and SHA-256 still match what was put there. The file is deleted once the image is written or the export ends, whether it succeeds, fails or is cancelled, and so is a folder made for it that is empty then; nothing the export did not make is deleted. A file that cannot be deleted, as when another program has it open, is left and named in the Output panel. The export holds the SHA-256 of a file it compares against, not the file's bytes. The export commands refuse a document or a folder of more than 1,000 named diagrams, and a folder of more than 500 documents, rather than export part of it.

*Check Export Freshness* (`src/export/freshness.ts`) writes nothing — no image, no document and no record — and draws nothing. It refuses to run in an untrusted workspace, by the same runtime check, and for a document not saved to disk. For the document in the editor, it reads the records of that document's exports; the files at the paths its diagrams are exported to, through `workspace.fs`, only a regular file of at most 64 MiB, its size looked at before it is read and again after, and no symbolic link, which is reported as one rather than followed — though a link put in a file's place between that look and the read is not caught; and the files its diagrams include, asked for as an export asks for them just before it writes, under the same checks and limits, an open document with its unsaved changes. It compares SHA-256s and keeps none of the text or bytes it reads. The marked image links are read from the document's text and resolved against its folder; nothing they name is fetched or opened. Picking an image from its list runs the export command for that diagram, which asks what it always asks; picking a link moves the cursor to its line; picking a recorded image selects it in the Explorer — each only while the document is as it was when it was checked.

Exporting on save (`src/export/auto-sync.ts`, the permissions in `src/export/permits.ts`) is the one export that writes without a command being run for it. It writes only the SVG file of a diagram given a permission by hand, one diagram at a time, with *Enable SVG Auto Export for Diagram*, after a modal that names the file; only while `plantumlLocal.autoExport.enabled` is on — a `machine` setting, which VS Code takes from User or Remote settings only, so that a workspace's or folder's own value is not used, and does not sync — and the workspace is trusted, both looked at when a file is saved and again just before writing; and only on VS Code's save of the diagram's document, of a file its last export read or looked for, or of a file an export since looked for, never on a change on disk. Each permission is kept in the workspace's state on the computer the window runs on, under `svgAutoExport`: the diagram as its export record names it, the SVG file's URI, the workspace folder's URI, where its includes are looked for, the include setting as written, the engine's version, a SHA-256 of the files that draw and the version of what the extension does after the engine, the palette, and 128 random bits made for each permission given, so that one given again is not taken for the one before. Each is checked field by field as it is read; one that is not as this version writes it, or one of two for the same diagram, grants nothing; at most 128 are kept; and permissions of a later version are read as none and left as they are. A permission is removed once any of what it holds is otherwise when the diagram would be exported, once a file written cannot be recorded as the diagram's export, and once the diagram is gone from its document or shares its name with another there — which each save of the document looks at, exporting on save on or not, so that a diagram given the name later is not exported under it. The diagram is drawn from saved files only, its includes read under the checks above: when the document or a file it includes is open with unsaved changes, nothing is written. The file is replaced only when it is there — as `workspace.fs` reports it, a regular file, no symbolic link and no larger than 64 MiB — is not open with unsaved changes, and is still what the record says this diagram's export wrote; under the lock the export commands take, the file, its record, what the diagram was drawn from and the permission are looked at again just before the rename that puts the new file in place. A file that is gone is not made again, nothing else is written — no image link, no document — and nothing is tried again until the next save. Diagrams are exported one at a time, half a second after their files were last saved, with at most one running and one waiting per diagram, each after what the previews are waiting to draw.

### Supply chain notes

- `@plantuml/core` is pinned to one exact version, never earlier than 1.2026.6, the first MIT-licensed release (see `package.json`), and its engine files are copied into the package (no CDN at build or run time): `plantuml.js`, `viz-global.cjs` and the OpenIconic icons verbatim, and the `!theme` library rebuilt without the themes this extension does not ship.
- Copyright and licence notices for every third-party component shipped in the VSIX are in [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md), with full licence texts under `third-party/`.
- happy-dom ships a self-signed TLS certificate (private key included) for HTTPS emulation in its fetch stack. This extension never uses that stack; the build replaces the certificate module with an empty stub, and `verify-vsix` fails the build if key material reappears in the bundle.

### Denial-of-service containment

Rendering pathological input is CPU-bound inside the worker, and renders are serialised, so a hung render would wedge the queue. Each render has a 30-second ceiling; on timeout the request fails, the worker is terminated and a fresh one serves the next request. The preview and the extension host stay responsive throughout.

Input can also make Graphviz crash, and the WebAssembly Graphviz then fails every later layout in the same worker. A diagram that crashes it gets the engine's crash report, and the worker is replaced the same way, so the diagrams after it — in any document — are laid out by a fresh Graphviz.

## Known Limitations

- The engine itself is a large compiled artifact (TeaVM output); we treat it as trusted upstream code and pin its version.
- A hostile document can still waste CPU in 30-second increments (one worker thread at a time); it cannot block the editor.
- Text metrics in the worker are approximated, so rendered layout can differ slightly from a browser rendering of the same diagram. This is a fidelity limitation, not a security one, but it is worth knowing when comparing output against plantuml.com.
